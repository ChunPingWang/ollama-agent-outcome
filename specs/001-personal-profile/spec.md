# Spec 001 — 個人資料管理

## 背景
系統需要為使用者提供管理個人基本資料的功能，包含建立、查詢、更新與刪除個人資料。此功能為核心業務模組，需確保資料的完整性與一致性，並提供標準化的 RESTful API 供前端或其他服務呼叫。

## 名詞
- **個人資料 (Profile)**：代表單一使用者的基本資訊集合，包含唯一識別碼、電子郵件、姓名與簡介。
- **電子郵件 (Email)**：用於識別使用者的唯一字串，需符合標準電子郵件格式，且在系統中必須唯一。
- **姓名 (Name)**：使用者的顯示名稱，不可為空。
- **簡介 (Bio)**：使用者的自我介紹，可選欄位，若未提供則視為空字串。

## 使用者情境

### US-1 建立個人資料
身為系統管理員，我想要建立新的個人資料，以便在系統中註冊新使用者。

### US-2 查詢個人資料
身為使用者，我想要透過 ID 查詢我的個人資料，以便確認我的資料是否正確。

### US-3 更新個人資料
身為使用者，我想要更新我的個人資料，以便修正錯誤資訊或更新現況。

### US-4 刪除個人資料
身為系統管理員，我想要刪除不再需要的個人資料，以便維護系統資料的潔淨。

## 驗收條件

```gherkin
功能: 個人資料 CRUD 操作
  作為 系統管理員或使用者
  我想要 建立、查詢、更新與刪除個人資料
  以便 管理系統中的使用者基本資訊

  場景: 成功建立新的個人資料
    假設 電子郵件 "alice@example.com" 在系統中尚不存在
    當 我發送 POST 請求至 "/profiles"，內容包含:
      | 欄位     | 值                  |
      | email    | alice@example.com   |
      | name     | Alice               |
      | bio      | Hello World         |
    那麼 回應狀態碼應為 201 Created
    並且 回應標頭 "Location" 應包含新建立的個人資料 ID
    並且 回應主體應包含新建立的個人資料資訊

  場景: 建立個人資料時電子郵件重複
    假設 電子郵件 "bob@example.com" 已存在於系統中
    當 我發送 POST 請求至 "/profiles"，內容包含:
      | 欄位     | 值                |
      | email    | bob@example.com   |
      | name     | Bob               |
      | bio      | Test              |
    那麼 回應狀態碼應為 409 Conflict
    並且 回應主體應指出電子郵件已存在

  場景: 建立個人資料時電子郵件格式無效
    當 我發送 POST 請求至 "/profiles"，內容包含:
      | 欄位     | 值          |
      | email    | invalid     |
      | name     | Invalid     |
      | bio      | Test        |
    那麼 回應狀態碼應為 400 Bad Request
    並且 回應主體應指出電子郵件格式錯誤

  場景: 建立個人資料時姓名為空
    當 我發送 POST 請求至 "/profiles"，內容包含:
      | 欄位     | 值          |
      | email    | empty@test.com |
      | name     |             |
      | bio      | Test        |
    那麼 回應狀態碼應為 400 Bad Request
    並且 回應主體應指出姓名不可為空

  場景: 成功查詢存在的個人資料
    假設 系統中已存在 ID 為 "uuid-123" 的個人資料，其電子郵件為 "charlie@example.com"
    當 我發送 GET 請求至 "/profiles/uuid-123"
    那麼 回應狀態碼應為 200 OK
    並且 回應主體應包含該個人資料的正確資訊

  場景: 查詢不存在的個人資料
    當 我發送 GET 請求至 "/profiles/non-existent-id"
    那麼 回應狀態碼應為 404 Not Found
    並且 回應主體應指出找不到該個人資料

  場景: 成功更新個人資料
    假設 系統中已存在 ID 為 "uuid-456" 的個人資料，其姓名為 "Old Name"
    當 我發送 PUT 請求至 "/profiles/uuid-456"，內容包含:
      | 欄位     | 值            |
      | email    | old@test.com  |
      | name     | New Name      |
      | bio      | Updated Bio   |
    那麼 回應狀態碼應為 200 OK
    並且 回應主體應包含更新後的個人資料資訊，其中姓名應為 "New Name"

  場景: 更新個人資料時指定不存在的 ID
    當 我發送 PUT 請求至 "/profiles/non-existent-id"，內容包含:
      | 欄位     | 值            |
      | email    | test@test.com |
      | name     | Test          |
      | bio      | Test          |
    那麼 回應狀態碼應為 404 Not Found
    並且 回應主體應指出找不到該個人資料

  場景: 成功刪除存在的個人資料
    假設 系統中已存在 ID 為 "uuid-789" 的個人資料
    當 我發送 DELETE 請求至 "/profiles/uuid-789"
    那麼 回應狀態碼應為 204 No Content
    並且 後續查詢該 ID 應返回 404 Not Found

  場景: 刪除不存在的個人資料
    當 我發送 DELETE 請求至 "/profiles/non-existent-id"
    那麼 回應狀態碼應為 404 Not Found
    並且 回應主體應指出找不到該個人資料
```

## API 概要

| 方法     | 路徑                  | 成功狀態碼 | 失敗狀態碼 | 說明                     |
|----------|-----------------------|------------|------------|--------------------------|
| POST     | /profiles             | 201        | 400, 409   | 建立新個人資料           |
| GET      | /profiles/{id}        | 200        | 404        | 查詢單一個人資料         |
| PUT      | /profiles/{id}        | 200        | 400, 404   | 全量更新個人資料         |
| DELETE   | /profiles/{id}        | 204        | 404        | 刪除個人資料             |

## 範圍外
- 個人資料的分頁查詢與列表獲取（僅支援單一 ID 查詢）。
- 個人資料的搜尋功能（如依姓名搜尋）。
- 個人資料的歷史版本追蹤或審計日誌。
- 使用者認證與授權（假設呼叫端已具備合法權限）。
