# Spec 001 — 個人資料管理

## 背景
系統需要為使用者提供管理個人基本資料的功能，包括建立新的個人資料、查詢現有資料、更新資料內容以及刪除不再需要的資料。此功能需確保資料的完整性與一致性，並提供清晰的錯誤回饋。

## 名詞
- **個人資料 (Profile)**：代表一個使用者的基本資訊集合，包含唯一的識別碼、電子郵件地址、顯示名稱與簡介。
- **電子郵件地址 (Email)**：用於唯一標識使用者的字串，需符合標準電子郵件格式。
- **顯示名稱 (Display Name)**：使用者在系統中顯示的名稱，允許為空或包含一般字元。
- **簡介 (Bio)**：關於使用者的簡短描述，允許為空。

## 使用者情境

### US-1 建立個人資料
身為系統使用者，我想要建立一份新的個人資料，以便在系統中擁有我的基本資訊。

### US-2 查詢個人資料
身為系統使用者，我想要透過唯一識別碼查詢我的個人資料，以便確認資料內容或用於其他業務流程。

### US-3 更新個人資料
身為系統使用者，我想要更新我的個人資料（如顯示名稱或簡介），以便保持資訊的準確性。

### US-4 刪除個人資料
身為系統使用者，我想要刪除我的個人資料，以便移除不再需要的資料或響應隱私請求。

## 驗收條件

```gherkin
功能: 個人資料 CRUD 操作

  場景: 成功建立新的個人資料
    假設 沒有已存在的電子郵件為 "user@example.com" 的個人資料
    當 我發送 POST 請求至 "/profiles"，內容包含:
      | 欄位       | 值                |
      | email      | user@example.com  |
      | displayName| 測試使用者        |
      | bio        | 這是一個測試簡介  |
    那麼 回應狀態碼應為 201 (Created)
    並且 回應標頭 "Location" 應包含新建立的個人資料識別碼
    並且 回應主體應包含新建立的個人資料資訊，且識別碼非空

  場景: 建立個人資料時電子郵件格式錯誤
    當 我發送 POST 請求至 "/profiles"，內容包含:
      | 欄位       | 值           |
      | email      | invalid-email|
      | displayName| 測試使用者   |
      | bio        |              |
    那麼 回應狀態碼應為 400 (Bad Request)
    並且 回應主體應包含關於 "email" 欄位的驗證錯誤訊息

  場景: 建立個人資料時電子郵件已存在
    假設 已存在電子郵件為 "existing@example.com" 的個人資料
    當 我發送 POST 請求至 "/profiles"，內容包含:
      | 欄位       | 值                 |
      | email      | existing@example.com |
      | displayName| 重複使用者         |
      | bio        |                      |
    那麼 回應狀態碼應為 409 (Conflict)
    並且 回應主體應指出電子郵件已存在

  場景: 成功查詢存在的個人資料
    假設 已存在識別碼為 "profile-id-123" 的個人資料
    當 我發送 GET 請求至 "/profiles/profile-id-123"
    那麼 回應狀態碼應為 200 (OK)
    並且 回應主體應包含該個人資料的正確資訊

  場景: 查詢不存在的個人資料
    當 我發送 GET 請求至 "/profiles/non-existent-id"
    那麼 回應狀態碼應為 404 (Not Found)
    並且 回應主體應指出該個人資料不存在

  場景: 成功更新個人資料
    假設 已存在識別碼為 "profile-id-123" 的個人資料，其顯示名稱為 "舊名稱"
    當 我發送 PUT 請求至 "/profiles/profile-id-123"，內容包含:
      | 欄位       | 值           |
      | email      | user@example.com |
      | displayName| 新名稱       |
      | bio        | 更新的簡介   |
    那麼 回應狀態碼應為 200 (OK)
    並且 回應主體應包含更新後的個人資料資訊，顯示名稱應為 "新名稱"

  場景: 更新不存在的個人資料
    當 我發送 PUT 請求至 "/profiles/non-existent-id"，內容包含:
      | 欄位       | 值           |
      | email      | user@example.com |
      | displayName| 新名稱       |
      | bio        |              |
    那麼 回應狀態碼應為 404 (Not Found)

  場景: 成功刪除個人資料
    假設 已存在識別碼為 "profile-id-123" 的個人資料
    當 我發送 DELETE 請求至 "/profiles/profile-id-123"
    那麼 回應狀態碼應為 204 (No Content)
    並且 回應主體應為空

  場景: 刪除不存在的個人資料
    當 我發送 DELETE 請求至 "/profiles/non-existent-id"
    那麼 回應狀態碼應為 404 (Not Found)
```

## API 概要

| 方法     | 路徑                         | 成功狀態碼 | 失敗狀態碼 | 說明                     |
|----------|------------------------------|------------|------------|--------------------------|
| POST     | /profiles                    | 201        | 400, 409   | 建立新個人資料           |
| GET      | /profiles/{id}               | 200        | 404        | 查詢單一個人資料         |
| PUT      | /profiles/{id}               | 200        | 400, 404   | 全量更新個人資料         |
| DELETE   | /profiles/{id}               | 204        | 404        | 刪除個人資料             |

## 範圍外
- 個人資料的分頁查詢與列表獲取（僅支援單一 ID 查詢）。
- 個人資料的搜尋功能（如依名稱搜尋）。
- 個人資料的歷史版本追蹤或撤銷刪除。
- 使用者認證與授權（假設呼叫端已處理身份驗證，或此為內部服務）。
