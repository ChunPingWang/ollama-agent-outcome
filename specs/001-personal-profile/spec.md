# Spec 001 — 個人資料管理

## 背景
系統需要為使用者提供管理個人基本資料的功能，包含建立、查詢、更新與刪除個人資料。此功能需確保資料的完整性與一致性，並提供清晰的錯誤回應以協助前端或客戶端進行處理。

## 名詞
- **個人資料 (Profile)**：代表單一使用者的基本資訊集合，包含唯一識別碼、姓名、電子郵件地址與備註。
- **電子郵件地址 (Email)**：用於識別使用者的唯一字串，需符合標準電子郵件格式，且在系統中必須唯一。
- **識別碼 (ID)**：系統自動產生的唯一識別字，用於標識每一筆個人資料。

## 使用者情境

### US-1 建立個人資料
身為系統使用者，我想要建立新的個人資料，以便在系統中註冊我的基本資訊。

### US-2 查詢個人資料
身為系統使用者，我想要透過識別碼查詢特定的個人資料，以便確認資料內容或進行後續操作。

### US-3 更新個人資料
身為系統使用者，我想要更新已有的個人資料，以便修正錯誤資訊或更新現況。

### US-4 刪除個人資料
身為系統使用者，我想要刪除不再需要的個人資料，以便維護資料的潔淨與隱私。

## 驗收條件

```gherkin
功能: 個人資料 CRUD 操作
  作為 系統使用者
  我想要 建立、查詢、更新與刪除個人資料
  以便 管理我的基本資訊

  場景: 成功建立新的個人資料
    當 我發送 POST 請求至 "/profiles"，內容包含:
      """
      {
        "name": "王小明",
        "email": "xiaoming@example.com",
        "note": "測試資料"
      }
      """
    那麼 回應狀態碼應為 201
    並且 回應標頭 "Location" 應包含新建立的個人資料識別碼
    並且 回應主體應包含新建立的個人資料資訊，且識別碼非空

  場景: 建立個人資料時電子郵件格式錯誤
    當 我發送 POST 請求至 "/profiles"，內容包含:
      """
      {
        "name": "王小明",
        "email": "invalid-email",
        "note": "測試資料"
      }
      """
    那麼 回應狀態碼應為 400
    並且 回應主體應包含錯誤訊息，指出電子郵件格式不合法

  場景: 建立個人資料時電子郵件已存在
    假設 系統中已存在電子郵件為 "existing@example.com" 的個人資料
    當 我發送 POST 請求至 "/profiles"，內容包含:
      """
      {
        "name": "李大明",
        "email": "existing@example.com",
        "note": "重複測試"
      }
      """
    那麼 回應狀態碼應為 409
    並且 回應主體應包含錯誤訊息，指出電子郵件已重複

  場景: 成功查詢存在的個人資料
    假設 系統中已存在識別碼為 "123e4567-e89b-12d3-a456-426614174000" 的個人資料
    當 我發送 GET 請求至 "/profiles/123e4567-e89b-12d3-a456-426614174000"
    那麼 回應狀態碼應為 200
    並且 回應主體應包含該個人資料的完整資訊

  場景: 查詢不存在的個人資料
    當 我發送 GET 請求至 "/profiles/00000000-0000-0000-0000-000000000000"
    那麼 回應狀態碼應為 404
    並且 回應主體應包含錯誤訊息，指出資料不存在

  場景: 成功更新個人資料
    假設 系統中已存在識別碼為 "123e4567-e89b-12d3-a456-426614174000" 的個人資料，其姓名為 "王小明"
    當 我發送 PUT 請求至 "/profiles/123e4567-e89b-12d3-a456-426614174000"，內容包含:
      """
      {
        "name": "王大明",
        "email": "xiaoming@example.com",
        "note": "更新後的備註"
      }
      """
    那麼 回應狀態碼應為 200
    並且 回應主體應包含更新後的個人資料資訊，姓名應為 "王大明"

  場景: 更新不存在的個人資料
    當 我發送 PUT 請求至 "/profiles/00000000-0000-0000-0000-000000000000"，內容包含:
      """
      {
        "name": "測試",
        "email": "test@example.com",
        "note": "測試"
      }
      """
    那麼 回應狀態碼應為 404
    並且 回應主體應包含錯誤訊息，指出資料不存在

  場景: 成功刪除個人資料
    假設 系統中已存在識別碼為 "123e4567-e89b-12d3-a456-426614174000" 的個人資料
    當 我發送 DELETE 請求至 "/profiles/123e4567-e89b-12d3-a456-426614174000"
    那麼 回應狀態碼應為 204
    並且 回應主體應為空

  場景: 刪除不存在的個人資料
    當 我發送 DELETE 請求至 "/profiles/00000000-0000-0000-0000-000000000000"
    那麼 回應狀態碼應為 404
    並且 回應主體應包含錯誤訊息，指出資料不存在
```

## API 概要

| HTTP 方法 | 路徑 | 成功狀態碼 | 失敗狀態碼 | 說明 |
| :--- | :--- | :--- | :--- | :--- |
| POST | `/profiles` | 201 | 400, 409 | 建立新個人資料 |
| GET | `/profiles/{id}` | 200 | 404 | 查詢單一個人資料 |
| PUT | `/profiles/{id}` | 200 | 400, 404, 409 | 更新單一個人資料 |
| DELETE | `/profiles/{id}` | 204 | 404 | 刪除單一個人資料 |

## 範圍外
- 個人資料的分頁查詢與列表獲取（僅支援單一 ID 查詢）。
- 個人資料的批量操作（Batch Create/Update/Delete）。
- 個人資料的歷史版本追蹤或審計日誌。
- 使用者認證與授權（假設所有請求均來自已認證使用者，或後續模組處理）。
