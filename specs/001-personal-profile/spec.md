# Spec 001 — 個人資料管理

## 背景
系統需要為使用者提供管理個人基本資料的功能，包含建立、查詢、更新與刪除個人資料。此功能需確保資料的完整性與一致性，並提供清晰的錯誤回應以協助前端或客戶端進行處理。

## 名詞
- **個人資料 (Profile)**：代表單一使用者的基本資訊集合，包含唯一識別碼、電子郵件、姓名與年齡。
- **電子郵件 (Email)**：用於識別使用者的唯一字串，需符合標準電子郵件格式。
- **姓名 (Name)**：使用者的顯示名稱，不可為空。
- **年齡 (Age)**：使用者的年齡，需為正整數。

## 使用者情境

### US-1 建立個人資料
身為系統管理員，我想要建立新的個人資料，以便在系統中註冊新使用者。

### US-2 查詢個人資料
身為使用者，我想要透過 ID 查詢我的個人資料，以便確認我的資料是否正確。

### US-3 更新個人資料
身為使用者，我想要更新我的個人資料，以便修正過時或不正確的資訊。

### US-4 刪除個人資料
身為系統管理員，我想要刪除不再需要的個人資料，以便維護系統資料的潔淨。

## 驗收條件

```gherkin
功能: 個人資料 CRUD 操作
  作為 系統管理員或使用者
  我想要 建立、查詢、更新與刪除個人資料
  以便 管理系統中的使用者基本資訊

  場景: 成功建立新的個人資料
    假設 電子郵件 "user@example.com" 尚未被使用
    當 我發送 POST 請求至 "/profiles" 並攜帶以下內容:
      | 欄位     | 值               |
      | email    | user@example.com |
      | name     | 測試使用者       |
      | age      | 25               |
    那麼 回應狀態碼應為 201 Created
    並且 回應內容應包含新建立的個人資料 ID
    並且 該 ID 可用於後續的查詢操作

  場景: 建立個人資料時電子郵件重複
    假設 電子郵件 "duplicate@example.com" 已存在於系統中
    當 我發送 POST 請求至 "/profiles" 並攜帶以下內容:
      | 欄位     | 值                  |
      | email    | duplicate@example.com |
      | name     | 重複使用者          |
      | age      | 30                  |
    那麼 回應狀態碼應為 409 Conflict
    並且 錯誤訊息應指出電子郵件已存在

  場景: 建立個人資料時電子郵件格式無效
    當 我發送 POST 請求至 "/profiles" 並攜帶以下內容:
      | 欄位     | 值             |
      | email    | invalid-email  |
      | name     | 測試使用者     |
      | age      | 25             |
    那麼 回應狀態碼應為 400 Bad Request
    並且 錯誤訊息應指出電子郵件格式不正確

  場景: 建立個人資料時年齡無效
    當 我發送 POST 請求至 "/profiles" 並攜帶以下內容:
      | 欄位     | 值   |
      | email    | new@example.com |
      | name     | 測試使用者     |
      | age      | -5             |
    那麼 回應狀態碼應為 400 Bad Request
    並且 錯誤訊息應指出年齡必須為正整數

  場景: 成功查詢存在的個人資料
    假設 系統中已存在 ID 為 "profile-123" 的個人資料
    當 我發送 GET 請求至 "/profiles/profile-123"
    那麼 回應狀態碼應為 200 OK
    並且 回應內容應包含該個人資料的 email, name, age

  場景: 查詢不存在的個人資料
    當 我發送 GET 請求至 "/profiles/non-existent-id"
    那麼 回應狀態碼應為 404 Not Found
    並且 錯誤訊息應指出找不到該個人資料

  場景: 成功更新個人資料
    假設 系統中已存在 ID 為 "profile-123" 的個人資料，其 name 為 "舊名稱"
    當 我發送 PUT 請求至 "/profiles/profile-123" 並攜帶以下內容:
      | 欄位     | 值         |
      | email    | user@example.com |
      | name     | 新名稱     |
      | age      | 26         |
    那麼 回應狀態碼應為 200 OK
    並且 回應內容應反映更新後的資料

  場景: 更新不存在的個人資料
    當 我發送 PUT 請求至 "/profiles/non-existent-id" 並攜帶以下內容:
      | 欄位     | 值               |
      | email    | user@example.com |
      | name     | 新名稱           |
      | age      | 26               |
    那麼 回應狀態碼應為 404 Not Found

  場景: 成功刪除個人資料
    假設 系統中已存在 ID 為 "profile-123" 的個人資料
    當 我發送 DELETE 請求至 "/profiles/profile-123"
    那麼 回應狀態碼應為 204 No Content
    並且 隨後發送 GET 請求至 "/profiles/profile-123" 應返回 404 Not Found

  場景: 刪除不存在的個人資料
    當 我發送 DELETE 請求至 "/profiles/non-existent-id"
    那麼 回應狀態碼應為 404 Not Found
```

## API 概要

| HTTP 方法 | 路徑                  | 成功狀態碼 | 失敗狀態碼 | 說明             |
|-----------|-----------------------|------------|------------|------------------|
| POST      | /profiles             | 201        | 400, 409   | 建立新個人資料   |
| GET       | /profiles/{id}        | 200        | 404        | 查詢單一個人資料 |
| PUT       | /profiles/{id}        | 200        | 400, 404   | 更新單一個人資料 |
| DELETE    | /profiles/{id}        | 204        | 404        | 刪除單一個人資料 |

## 範圍外
- 個人資料的分頁查詢與列表獲取（僅支援單一 ID 查詢）。
- 個人資料的批量建立或更新。
- 個人資料的軟刪除（Soft Delete）機制。
- 使用者認證與授權（假設呼叫端已具備適當權限）。
- 個人資料的歷史版本追蹤。
