# Spec 001 — 個人資料管理

## 背景
系統需要為使用者提供管理個人資料的功能，包括建立新的個人資料、查詢現有資料、更新個人資訊以及刪除不再需要的資料。此功能需確保資料的完整性與一致性，並提供清晰的錯誤回饋。

## 名詞
- **個人資料 (Profile)**：代表一個使用者的基本資訊集合，包含唯一識別碼、姓名、電子郵件地址等欄位。
- **電子郵件 (Email)**：用於識別使用者的唯一字串，需符合標準電子郵件格式，且在系統中必須唯一。
- **識別碼 (ID)**：系統自動產生的唯一識別字，用於標識每一筆個人資料。

## 使用者情境

### US-1 建立個人資料
身為系統使用者，我想要建立新的個人資料，以便在系統中註冊我的基本資訊。

### US-2 查詢個人資料
身為系統使用者，我想要透過識別碼查詢特定的個人資料，以便確認資料內容或進行後續操作。

### US-3 更新個人資料
身為系統使用者，我想要更新我的個人資料，以便修正錯誤資訊或更新現況。

### US-4 刪除個人資料
身為系統使用者，我想要刪除我的個人資料，以便移除不再需要的資料或符合隱私刪除請求。

## 驗收條件

```gherkin
功能: 個人資料 CRUD 操作

  場景: 成功建立新的個人資料
    假設 沒有已存在的電子郵件為 "user@example.com" 的個人資料
    當 我發送 POST 請求至 "/profiles" 並帶入以下內容:
      | 欄位 | 值 |
      | name | 張三 |
      | email | user@example.com |
    那麼 回應狀態碼應為 201 Created
    並且 回應標頭 "Location" 應包含新建立的個人資料識別碼
    並且 回應內容應包含新建立的個人資料識別碼

  場景: 建立個人資料時電子郵件重複
    假設 已存在電子郵件為 "duplicate@example.com" 的個人資料
    當 我發送 POST 請求至 "/profiles" 並帶入以下內容:
      | 欄位 | 值 |
      | name | 李四 |
      | email | duplicate@example.com |
    那麼 回應狀態碼應為 409 Conflict
    並且 回應內容應指出電子郵件已存在

  場景: 建立個人資料時電子郵件格式無效
    當 我發送 POST 請求至 "/profiles" 並帶入以下內容:
      | 欄位 | 值 |
      | name | 王五 |
      | email | invalid-email |
    那麼 回應狀態碼應為 400 Bad Request
    並且 回應內容應指出電子郵件格式錯誤

  場景: 成功查詢存在的個人資料
    假設 已存在識別碼為 "uuid-123" 的個人資料，其姓名為 "趙六"
    當 我發送 GET 請求至 "/profiles/uuid-123"
    那麼 回應狀態碼應為 200 OK
    並且 回應內容中的姓名應為 "趙六"
    並且 回應內容中的電子郵件應與建立時一致

  場景: 查詢不存在的個人資料
    當 我發送 GET 請求至 "/profiles/non-existent-id"
    那麼 回應狀態碼應為 404 Not Found
    並且 回應內容應指出找不到該個人資料

  場景: 成功更新個人資料
    假設 已存在識別碼為 "uuid-456" 的個人資料，其姓名為 "錢七"
    當 我發送 PUT 請求至 "/profiles/uuid-456" 並帶入以下內容:
      | 欄位 | 值 |
      | name | 錢七更新後 |
      | email | qian@example.com |
    那麼 回應狀態碼應為 200 OK
    並且 回應內容中的姓名應為 "錢七更新後"
    並且 回應內容中的電子郵件應為 "qian@example.com"

  場景: 更新不存在的個人資料
    當 我發送 PUT 請求至 "/profiles/non-existent-id" 並帶入以下內容:
      | 欄位 | 值 |
      | name | 無名氏 |
      | email | nobody@example.com |
    那麼 回應狀態碼應為 404 Not Found

  場景: 成功刪除個人資料
    假設 已存在識別碼為 "uuid-789" 的個人資料
    當 我發送 DELETE 請求至 "/profiles/uuid-789"
    那麼 回應狀態碼應為 204 No Content
    並且 再次發送 GET 請求至 "/profiles/uuid-789" 時應返回 404 Not Found

  場景: 刪除不存在的個人資料
    當 我發送 DELETE 請求至 "/profiles/non-existent-id"
    那麼 回應狀態碼應為 404 Not Found
```

## API 概要

| HTTP 方法 | 路徑 | 描述 | 成功狀態碼 | 失敗狀態碼 |
| :--- | :--- | :--- | :--- | :--- |
| POST | `/profiles` | 建立新的個人資料 | 201 Created | 400 Bad Request, 409 Conflict |
| GET | `/profiles/{id}` | 查詢特定個人資料 | 200 OK | 404 Not Found |
| PUT | `/profiles/{id}` | 更新特定個人資料 | 200 OK | 400 Bad Request, 404 Not Found |
| DELETE | `/profiles/{id}` | 刪除特定個人資料 | 204 No Content | 404 Not Found |

## 範圍外
- 個人資料的分頁查詢與列表獲取（僅支援單一識別碼查詢）。
- 個人資料的搜尋功能（如依姓名搜尋）。
- 個人資料的歷史版本追蹤或復原功能。
- 使用者認證與授權（假設所有請求均來自已認證使用者，或此為公開服務）。
