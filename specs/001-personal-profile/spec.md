# Spec 001 — 個人資料管理

## 背景
系統需要為使用者提供管理個人資料的功能，包括建立新的個人資料、查詢現有資料、更新個人資訊以及刪除不再需要的資料。此功能需確保資料的完整性與一致性，並提供清晰的錯誤回饋。

## 名詞
- **個人資料 (Profile)**：代表一個使用者的基本資訊集合，包含唯一識別碼、姓名、電子郵件地址等欄位。
- **電子郵件地址 (Email)**：用於識別使用者的唯一字串，需符合標準電子郵件格式，且在系統中必須唯一。
- **識別碼 (ID)**：個人資料的唯一標識符，由系統在建立時自動生成。

## 使用者情境

### US-1 建立個人資料
身為系統使用者，我想要建立一個新的個人資料，以便在系統中擁有我的基本資訊記錄。

### US-2 查詢個人資料
身為系統使用者，我想要透過識別碼查詢我的個人資料，以便確認我的資訊是否正確。

### US-3 更新個人資料
身為系統使用者，我想要更新我的個人資料（如姓名或電子郵件），以便保持資訊的時效性。

### US-4 刪除個人資料
身為系統使用者，我想要刪除我的個人資料，以便移除不再需要的資料。

## 驗收條件

```gherkin
功能: 個人資料 CRUD 操作
    作為系統使用者
    我想要管理我的個人資料
    以便維護我的基本資訊

    場景: 成功建立個人資料
        假設 系統中不存在電子郵件為 "user@example.com" 的個人資料
        當 我提交建立個人資料的請求，包含姓名 "張三" 與電子郵件 "user@example.com"
        那麼 回應狀態碼應為 201 Created
        並且 回應內容應包含新生成的識別碼
        並且 系統中應存在該筆個人資料

    場景: 建立個人資料時電子郵件重複
        假設 系統中已存在電子郵件為 "duplicate@example.com" 的個人資料
        當 我提交建立個人資料的請求，包含姓名 "李四" 與電子郵件 "duplicate@example.com"
        那麼 回應狀態碼應為 409 Conflict
        並且 錯誤訊息應指出電子郵件已存在

    場景: 建立個人資料時電子郵件格式無效
        假設 系統中不存在電子郵件為 "invalid-email" 的個人資料
        當 我提交建立個人資料的請求，包含姓名 "王五" 與電子郵件 "invalid-email"
        那麼 回應狀態碼應為 400 Bad Request
        並且 錯誤訊息應指出電子郵件格式不正確

    場景: 成功查詢存在的個人資料
        假設 系統中存在識別碼為 "uuid-123" 的個人資料，姓名為 "張三"
        當 我查詢識別碼為 "uuid-123" 的個人資料
        那麼 回應狀態碼應為 200 OK
        並且 回應內容應包含姓名 "張三" 與正確的電子郵件

    場景: 查詢不存在的個人資料
        假設 系統中不存在識別碼為 "uuid-nonexistent" 的個人資料
        當 我查詢識別碼為 "uuid-nonexistent" 的個人資料
        那麼 回應狀態碼應為 404 Not Found
        並且 錯誤訊息應指出資料不存在

    場景: 成功更新個人資料
        假設 系統中存在識別碼為 "uuid-123" 的個人資料，姓名為 "張三"，電子郵件為 "old@example.com"
        當 我更新識別碼為 "uuid-123" 的個人資料，將姓名改為 "張三豐"，電子郵件改為 "new@example.com"
        那麼 回應狀態碼應為 200 OK
        並且 系統中的資料應更新為新的姓名與電子郵件

    場景: 更新個人資料時電子郵件重複
        假設 系統中存在識別碼為 "uuid-123" 的個人資料，且另存在識別碼為 "uuid-456" 的個人資料，電子郵件為 "target@example.com"
        當 我更新識別碼為 "uuid-123" 的個人資料，將電子郵件改為 "target@example.com"
        那麼 回應狀態碼應為 409 Conflict
        並且 錯誤訊息應指出電子郵件已存在

    場景: 更新不存在的個人資料
        假設 系統中不存在識別碼為 "uuid-nonexistent" 的個人資料
        當 我更新識別碼為 "uuid-nonexistent" 的個人資料
        那麼 回應狀態碼應為 404 Not Found
        並且 錯誤訊息應指出資料不存在

    場景: 成功刪除個人資料
        假設 系統中存在識別碼為 "uuid-123" 的個人資料
        當 我刪除識別碼為 "uuid-123" 的個人資料
        那麼 回應狀態碼應為 204 No Content
        並且 系統中該筆資料應被移除

    場景: 刪除不存在的個人資料
        假設 系統中不存在識別碼為 "uuid-nonexistent" 的個人資料
        當 我刪除識別碼為 "uuid-nonexistent" 的個人資料
        那麼 回應狀態碼應為 404 Not Found
        並且 錯誤訊息應指出資料不存在
```

## API 概要

| 方法 | 路徑 | 描述 | 成功狀態碼 | 失敗狀態碼 |
| :--- | :--- | :--- | :--- | :--- |
| POST | `/api/profiles` | 建立新個人資料 | 201 | 400 (驗證失敗), 409 (重複) |
| GET | `/api/profiles/{id}` | 查詢單一個人資料 | 200 | 404 (找不到) |
| PUT | `/api/profiles/{id}` | 更新單一個人資料 | 200 | 400 (驗證失敗), 404 (找不到), 409 (重複) |
| DELETE | `/api/profiles/{id}` | 刪除單一個人資料 | 204 | 404 (找不到) |

## 範圍外
- 個人資料的分頁與列表查詢（僅支援單一 ID 查詢）。
- 個人資料的批量操作。
- 使用者認證與授權（假設請求已通過基礎認證）。
- 個人資料的歷史版本追蹤。
