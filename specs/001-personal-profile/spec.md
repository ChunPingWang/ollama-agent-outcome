# Spec 001 — 個人資料管理 (Personal Profile CRUD)

## 背景
系統需要為註冊用戶提供維護個人基本資訊的功能。用戶可以建立自己的個人資料，並隨時查看、修改或刪除該資料。系統需確保資料的完整性與唯一性（特別是電子郵件地址），並在發生錯誤時給予明確的回報。

## 名詞
- **個人資料 (Profile)**：代表單一用戶的基本資訊集合，包含唯一的識別碼、姓名、電子郵件地址與簡介。
- **電子郵件 (Email)**：用於標識用戶的唯一聯絡方式，格式必須符合標準 Email 規範，且在系統中不得重複。
- **識別碼 (ID)**：系統自動產生的唯一識別符，用於區分不同的個人資料記錄。

## 使用者情境

### US-1 新增個人資料
身為一位新用戶，我想要建立我的個人資料以便開始使用系統服務。

### US-2 查詢個人資料
身為一位已登入用戶，我想要根據 ID 查詢我的個人資料詳細資訊，以便確認當前儲存的狀態。

### US-3 更新個人資料
身為一位已登入用戶，我想要修改我的個人資料（如姓名或簡介），以便保持資訊的最新性。

### US-4 刪除個人資料
身為一位已登入用戶，我想要刪除我的個人資料，以便停止使用服務或保護隱私。

## 驗收條件

```gherkin
功能: 個人資料 CRUD
    作為一名用戶
    我希望能夠管理我的個人資料
    
    場景: 成功建立新的個人資料
        假設 我沒有名為 "test@example.com" 的個人資料
        當 我發送 POST 請求至 "/profiles"，內容包含:
            """
            {
              "name": "王小明",
              "email": "test@example.com",
              "bio": "這是一個測試資料"
            }
            """
        那麼 回應的狀態碼應該是 201 (Created)
        並且 回應標頭 "Location" 應該存在且指向該資源的路徑
        
    場景: 嘗試建立重複電子郵件的個人資料失敗
        假設 我已有一個名稱為 "王小明"、電子郵件為 "duplicate@test.com" 的個人資料
        當 我發送 POST 請求至 "/profiles"，內容包含:
            """
            {
              "name": "李大明",
              "email": "duplicate@test.com",
              "bio": "試圖重複註冊"
            }
            """
        那麼 回應的狀態碼應該是 409 (Conflict)
        
    場景: 嘗試建立格式錯誤的電子郵件失敗
        當 我發送 POST 請求至 "/profiles"，內容包含:
            """
            {
              "name": "王小明",
              "email": "invalid-email-format",
              "bio": "無效 email"
            }
            """
        那麼 回應的狀態碼應該是 400 (Bad Request)

    場景: 成功查詢存在的個人資料
        假設 已存在一個 ID 為 "{uuid}" 的個人資料，其姓名為 "王小明"
        當 我發送 GET 請求至 "/profiles/{id}"
        那麼 回應的狀態碼應該是 200 (OK)
        並且 回應的內容應該包含姓名 "王小明"
        
    場景: 查詢不存在的個人資料
        當 我發送 GET 請求至 "/profiles/00000000-0000-0000-0000-000000000001"
        那麼 回應的狀態碼應該是 404 (Not Found)

    場景: 成功更新個人資料
        假設 已存在一個 ID 為 "{uuid}" 的個人資料，其姓名為 "舊名字"
        當 我發送 PUT 請求至 "/profiles/{id}"，內容包含:
            """
            {
              "name": "新名字",
              "email": "test@example.com",
              "bio": "更新的簡介"
            }
            """
        那麼 回應的狀態碼應該是 200 (OK)
        並且 該資源的姓名應變更為 "新名字"
        
    場景: 嘗試更新不存在的個人資料
        當 我發送 PUT 請求至 "/profiles/00000000-0000-0000-0000-000000000001"，內容包含:
            """
            {
              "name": "無效資料",
              "email": "new@test.com",
              "bio": ""
            }
            """
        那麼 回應的狀態碼應該是 404 (Not Found)

    場景: 成功刪除個人資料
        假設 已存在一個 ID 為 "{uuid}" 的個人資料
        當 我發送 DELETE 請求至 "/profiles/{id}"
        那麼 回應的狀態碼應該是 204 (No Content)
        並且 再次查詢該 ID 時應返回 404
        
    場景: 刪除不存在的個人資料
        當 我發送 DELETE 請求至 "/profiles/00000000-0000-0000-0000-000000000001"
        那麼 回應的狀態碼應該是 404 (Not Found)
```

## API 概要

| HTTP Method | Path | Description | Success Status | Error Status |
| :--- | :--- | :--- | :--- | :--- |
| POST | `/profiles` | 建立新個人資料 | 201 Created | 400 Bad Request, 409 Conflict |
| GET | `/profiles/{id}` | 根據 ID 查詢資料 | 200 OK | 404 Not Found |
| PUT | `/profiles/{id}` | 全量更新資料 | 200 OK | 400 Bad Request, 404 Not Found |
| DELETE | `/profiles/{id}` | 刪除指定資料 | 204 No Content | 404 Not Found |
