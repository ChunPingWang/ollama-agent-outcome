# Spec 001 — 個人資料管理 (Personal Profile CRUD)

## 背景
系統需要為註冊用戶提供維護個人基本資訊的功能。用戶可以建立自己的個人資料，並隨時查看、修改或刪除這些資訊。這確保了數據的準確性與用戶對自身數據的控制權。

## 名詞
- **個人資料 (Profile)**：代表單一用戶的基本靜態資訊集合，包含唯一識別碼、姓名、電子郵件地址等。
- **電子郵件 (Email)**：用於標識用戶的唯一聯絡方式，格式需符合標準 Email 規範，且在系統中必須保持唯一。
- **識別碼 (ID)**：系統自動生成的全局唯一標識符，用於區分不同的個人資料記錄。

## 使用者情境

### US-1 新增個人資料
身為**新用戶**，我想要**建立我的個人資料**，以便**後續使用系統功能**。

### US-2 查詢個人資料
身為**已登入用戶**，我想要**根據 ID 查詢我的個人資料**，以便**確認當前儲存的資料內容**。

### US-3 更新個人資料
身為**擁有個人資料的用戶**，我想要**修改我的姓名或電子郵件**，以便**保持資料的最新狀態**。

### US-4 刪除個人資料
身為**希望移除帳號的用戶**，我想要**永久刪除我的個人資料**，以便**不再被系統追蹤或聯繫**。

## 驗收條件

```gherkin
功能: 個人資料 CRUD 操作
    作為一名用戶
    我希望能夠對個人資料進行增刪改查
    以確保個人信息的準確性和安全性

    場景: 成功建立新的個人資料
        假設 系統中存在空的個人資料列表
        當 我發送 POST 請求至 "/profiles"，內容包含:
            """json
            {
              "name": "王小明",
              "email": "xiaoming@example.com"
            }
            """
        那麼 HTTP 狀態碼應為 201 (Created)
        並且 回應頭部 "Location" 應指向新建立的資源路徑
        並且 回應主體應包含新生成的識別碼、名稱與電子郵件

    場景: 嘗試建立重複電子郵件的個人資料失敗
        假設 系統中已存在電子郵件為 "duplicate@test.com" 的個人資料
        當 我發送 POST 請求至 "/profiles"，內容包含:
            """json
            {
              "name": "李大明",
              "email": "duplicate@test.com"
            }
            """
        那麼 HTTP 狀態碼應為 409 (Conflict)
        並且 錯誤訊息應指出電子郵件已被使用

    場景: 嘗試建立無效格式電子郵件的個人資料失敗
        當 我發送 POST 請求至 "/profiles"，內容包含:
            """json
            {
              "name": "張三",
              "email": "invalid-email-format"
            }
            """
        那麼 HTTP 狀態碼應為 400 (Bad Request)
        並且 錯誤訊息應提示電子郵件格式不正確

    場景: 成功查詢存在的個人資料
        假設 系統中存在 ID 為 "123e4567-e89b-12d3-a456-426614174000" 且名稱為 "王小明" 的個人資料
        當 我發送 GET 請求至 "/profiles/123e4567-e89b-12d3-a456-426614174000"
        那麼 HTTP 狀態碼應為 200 (OK)
        並且 回應主體中的名稱應為 "王小明"
        並且 回應主體中的識別碼應與路徑參數一致

    場景: 查詢不存在的個人資料失敗
        當 我發送 GET 請求至 "/profiles/non-existent-id"
        那麼 HTTP 狀態碼應為 404 (Not Found)
        並且 錯誤訊息應指出該資料不存在

    場景: 成功更新個人資料
        假設 系統中存在 ID 為 "123e4567-e89b-12d3-a456-426614174000" 且名稱為 "舊名字"、電子郵件為 "old@test.com" 的個人資料
        當 我發送 PUT 請求至 "/profiles/123e4567-e89b-12d3-a456-426614174000"，內容包含:
            """json
            {
              "name": "新名字",
              "email": "new@test.com"
            }
            """
        那麼 HTTP 狀態碼應為 200 (OK)
        並且 再次查詢該 ID 時，名稱應變更為 "新名字"
        並且 再次查詢該 ID 時，電子郵件應變更為 "new@test.com"

    場景: 嘗試更新不存在的個人資料失敗
        當 我發送 PUT 請求至 "/profiles/non-existent-id"，內容包含:
            """json
            {
              "name": "無效資料",
              "email": "noexist@test.com"
            }
            """
        那麼 HTTP 狀態碼應為 404 (Not Found)

    場景: 成功刪除個人資料
        假設 系統中存在 ID 為 "123e4567-e89b-12d3-a456-426614174000" 的個人資料
        當 我發送 DELETE 請求至 "/profiles/123e4567-e89b-12d3-a456-426614174000"
        那麼 HTTP 狀態碼應為 204 (No Content)
        並且 隨後再查詢該 ID 時，應返回 404 Not Found

    場景: 嘗試刪除不存在的個人資料失敗
        當 我發送 DELETE 請求至 "/profiles/non-existent-id"
        那麼 HTTP 狀態碼應為 404 (Not Found)
```

## API 概要

| 方法 | 路徑 | 描述 | 成功狀態碼 | 失敗狀態碼 |
| :--- | :--- | :--- | :--- | :--- |
| POST | `/profiles` | 建立新個人資料 | 201 Created | 400 Bad Request, 409 Conflict |
| GET | `/profiles/{id}` | 根據 ID 查詢資料 | 200 OK | 404 Not Found |
| PUT | `/profiles/{id}` | 全量更新指定 ID 的資料 | 200 OK | 400 Bad Request, 404 Not Found |
| DELETE | `/profiles/{id}` | 永久刪除指定 ID 的資料 | 204 No Content | 404 Not Found |
