# Plan 001 — 個人資料管理 (Personal Profile CRUD)

本計畫基於 Spec 001 設計六角形架構的實現細節。

## 領域模型 (Domain Model)

### Value Objects & Entities

- **ProfileId** (`record`)
    - 內容：`UUID id`
    - 不變條件：不可為 null。
    - 用途：作為 Domain Entity 的唯一識別碼，並用於 JPA Entity 的主鍵映射。

- **Email** (`record`)
    - 內容：`String value`
    - 不變條件：符合 RFC 5322 基本格式（使用正則表達式驗證），長度限制在 254 以內，不允許空白字串或僅含空白。
    - 用途：確保電子郵件地址的有效性與唯一性語義。

- **DisplayName** (`record`)
    - 內容：`String value`
    - 不變條件：允許為 `null` 或空字串，但若存在則最大長度為 100 字元。
    - 用途：使用者顯示名稱。

- **Profile** (`class`, Immutable after creation except for mutable fields via methods)
    - 欄位：`ProfileId id`, `Email email`, `DisplayName displayName`
    - 不變條件：
        - ID 由系統產生（UUID）。
        - Email 必須有效且唯一（業務規則層面檢查重複，資料庫層面約束）。
        - DisplayName 若提供需符合長度限制。
    - 行為：
        - `updateDisplayName(DisplayName newName)`：回傳新的 Profile 實例或更新內部狀態（視不可變性嚴格程度而定，此處採用不可變設計，回傳新實例或透過 Builder/Factory，但考慮到 JPA Entity 轉換方便性，Domain Object 可視為值物件集合的容器，實際持久化由 Adapter 處理狀態變更）。*修正策略*：為了配合 Hexagonal 架構中 Application Service 調用 Port 的模式，Domain Entity 通常包含業務邏輯方法。這裡定義 `changeDisplayName` 方法來封裝更新邏輯。

### Domain Exceptions

- **DuplicateEmailException** (`RuntimeException`)
    - 觸發時機：嘗試建立具有已存在電子郵件的個人資料時。
    - 訊息："Email already exists"。

- **InvalidEmailException** (`IllegalArgumentException`)
    - 觸發時機：Email Value Object 初始化時格式無效。

- **ProfileNotFoundException** (`RuntimeException`)
    - 觸發時機：查詢、更新或删除不存在的 ID 時。

## Use Cases & Ports

### Inbound Ports (Use Case Interfaces)

1. **CreateProfileUseCase**
   ```java
   void execute(CreateProfileRequest request);
   // CreateProfileRequest: record { Email email, DisplayName displayName }
   ```

2. **GetProfileUseCase**
   ```java
   ProfileResult execute(ProfileId id);
   // ProfileResult: record { ProfileId id, Email email, DisplayName displayName }
   ```

3. **UpdateProfileUseCase**
   ```java
   void execute(UpdateProfileRequest request);
   // UpdateProfileRequest: record { ProfileId id, DisplayName displayName }
   ```

4. **DeleteProfileUseCase**
   ```java
   void execute(ProfileId id);
   ```

### Outbound Ports (Repository Interfaces)

位於 `application.port.out`，僅定義介面，由 Persistence Adapter 實作。

1. **SaveProfilePort**
   ```java
   Profile save(Profile profile);
   ```

2. **LoadProfilePort**
   ```java
   Optional<Profile> findById(ProfileId id);
   ```

3. **ExistsByEmailPort**
   ```java
   boolean existsByEmail(Email email);
   ```

4. **DeleteProfilePort**
   ```java
   void deleteById(ProfileId id);
   ```

*註：為符合 SOLID 與單一職責，將讀取、寫入、檢查存在性分離為不同 Port，儘管在簡單 CRUD 中可能合併，但為了架構清晰度與未來擴充（如分庫或異步處理），建議分開。若考慮簡化，可合併為一個 `ProfileRepositoryPort`，但根據 System Prompt "介面分離" 原則，這裡選擇細粒度 Port。然而，為了減少 boilerplate code 並保持實用性，通常 CRUD 會有一個統一的 Repository Interface。鑑於 Spec 需求單純，我們將創建一個綜合的 `ProfileRepositoryPort` 以減少耦合複雜度，除非有明確理由拆分。*
*修正*：System Prompt 提到 "port 介面小而專一... LoadProfilePort, SaveProfilePort 可分開"。我們遵循此建議，定義以下四個 Port。

## Web Adapter (REST API)

### Controller: `ProfileController`
路徑前綴：`/profiles`

- **POST /profiles**
    - DTO Input: `CreateProfileRequestDto { String email, String displayName }`
    - DTO Output: None (201 Created + Location header).
    - Logic: 驗證 DTO -> Call `CreateProfileUseCase`.
    - Exceptions:
        - Validation Error (`@Valid`) -> 400 Bad Request.
        - `DuplicateEmailException` -> 409 Conflict.
        - `InvalidEmailException` -> 400 Bad Request.

- **GET /profiles/{id}**
    - Path Variable: `String id` (UUID string).
    - DTO Output: `GetProfileResponseDto { UUID id, String email, String displayName }`.
    - Logic: Parse ID -> Call `GetProfileUseCase`.
    - Exceptions:
        - `ProfileNotFoundException` -> 404 Not Found.
        - Invalid UUID format -> 400 Bad Request (handled by global advice or controller try-catch).

- **PUT /profiles/{id}**
    - Path Variable: `String id`.
    - DTO Input: `UpdateProfileRequestDto { String displayName }`.
    - Logic: Parse ID -> Validate DTO -> Call `UpdateProfileUseCase`.
    - Exceptions:
        - `ProfileNotFoundException` -> 404 Not Found.
        - Validation Error -> 400 Bad Request.

- **DELETE /profiles/{id}**
    - Path Variable: `String id`.
    - Logic: Parse ID -> Call `DeleteProfileUseCase`.
    - Exceptions:
        - `ProfileNotFoundException` -> 404 Not Found.

### Exception Handler: `GlobalExceptionHandler` (`@RestControllerAdvice`)
- `MethodArgumentNotValidException` -> 400.
- `HttpMessageNotReadableException` -> 400.
- `DuplicateEmailException` -> 409.
- `ProfileNotFoundException` -> 404.
- *注意*：不攔截 `Exception.class`，以免覆蓋 Spring Boot 的預設 404/500 行為。

## Persistence Adapter (JPA)

### Entity: `ProfileEntity`
- Package: `com.github.chunpingwang.ollamaagentoutcome.adapter.persistence`
- Fields:
    - `UUID id`: Primary Key, Generated by Domain (UUID). Implements `Persistable<UUID>`.
    - `String email`: Unique Constraint, Indexed.
    - `String displayName`: Nullable.
- Methods:
    - `isNew()`: Returns true if newly created, false after persist/load. Managed via `@PostLoad`, `@PostPersist`.

### Repository Interface: `ProfileRepository` extends `JpaRepository<ProfileEntity, UUID>`
- Note: Since we defined specific Ports in Application layer, the JPA Repository is an internal detail of the Persistence Adapter. The Port implementations will inject this repository.

### Port Implementations (`adapter.persistence`)
1. **JpaSaveProfilePort** implements `SaveProfilePort`
   - Injects `ProfileRepository`.
   - Converts Domain `Profile` to `ProfileEntity`.
   - Calls `repository.saveAndFlush(entity)` to trigger unique constraint check immediately.
   - Catches `DataIntegrityViolationException` and throws `DuplicateEmailException`.

2. **JpaLoadProfilePort** implements `LoadProfilePort`
   - Injects `ProfileRepository`.
   - Calls `repository.findById(id)`.
   - Converts `Optional<Entity>` to `Optional<Domain Profile>`.

3. **JpaExistsByEmailPort** implements `ExistsByEmailPort`
   - Injects `ProfileRepository`.
   - Calls `repository.existsByEmail(email.getValue())`.

4. **JpaDeleteProfilePort** implements `DeleteProfilePort`
   - Injects `ProfileRepository`.
   - First checks existence via `findById` (or uses a method that throws if not found). To ensure 404 handling consistency with domain logic, it's better to load first or have a deleteById that returns void but we need to know if it existed.
   - *Strategy*: Call `load` first in the Use Case? No, Port should be efficient. Let's add `deleteByIdAndIdIn(List<UUID>)` or similar? Or simply: In `JpaDeleteProfilePort`, try to find by ID. If empty, throw specific exception or return boolean? The Domain Exception `ProfileNotFoundException` is thrown by Application Service usually. However, Persistence Adapter can also throw data access exceptions.
   - *Refinement*: It is cleaner for the Application Service (`DeleteProfileService`) to call `LoadProfilePort` first to verify existence and throw `ProfileNotFoundException` before calling `DeleteProfilePort`. This keeps DB operations minimal. So `DeleteProfilePort` just does `repository.deleteById(id)`. But wait, if I don't check existence, deleting non-existent might succeed silently in JPA. We want 404. So yes, **Application Layer** must check existence using `LoadProfilePort` before invoking `DeleteProfileUseCase`'s execution which calls `DeleteProfilePort`.

### Converter/Transformer
- Static methods or separate classes within adapter package to convert between `ProfileEntity` and `Profile`.

## Bootstrap Configuration

- Class: `UseCaseConfiguration` (in `bootstrap` module).
- Annotated with `@Configuration`.
- Defines `@Bean`s for all Use Case Services (`CreateProfileService`, etc.) and Port Implementations (`JpaSaveProfilePort`, etc.).
- Injects dependencies via constructor arguments defined in beans.

## Testing Strategy

1. **Domain Tests**: Pure JUnit + AssertJ. Test Value Object validation rules and Entity business logic. No Spring.
2. **Application Tests**: Pure JUnit + Mockito. Mock Outbound Ports. Verify that Use Cases correctly orchestrate ports and handle domain exceptions.
3. **Persistence Adapter Tests**: `@DataJpaTest` + Testcontainers PostgreSQL. Test Repository queries and Port implementations (conversion + DB interaction). Verify unique constraint handling.
4. **Web Adapter Tests**: `@WebMvcTest`. Mock Inbound Ports (or use a slice test? No, Web layer should be tested against mocked application services to isolate UI logic). Wait, System Prompt says "adapter-web 使用 @WebMvcTest". It implies mocking the service layer. We will mock the `*UseCase` interfaces or their implementation classes if they are beans. Since we are testing the Controller's mapping and exception translation, mocking the Application Service is appropriate.
5. **BDD/Cucumber**: Full integration tests using `@SpringBootTest` with Testcontainers. Features located in `bootstrap/src/test/resources/features/personal-profile-crud.feature`. Steps in `com.github.chunpingwang.ollamaagentoutcome.bdd`. Uses `TestRestTemplate` for HTTP calls.
