# Spec 001 — 個人資料管理 (Personal Profile CRUD)

## 背景
系統需要為註冊用戶提供維護個人基本資訊的功能，包括建立新的個人資料記錄、查詢現有資料、更新已存在的資訊以及刪除不再需要的資料。這確保了數據的準確性與完整性，並符合隱私保護的基本需求。

## 名詞
- **個人資料 (Profile)**：代表單一使用者的核心基本資訊集合，包含唯一識別碼、姓名、電子郵件地址等欄位。
- **電子郵件 (Email)**：用於標識使用者身份的唯一字串格式，需符合標準 Email 語法且在全域中必須唯一。
- **識別碼 (ID)**：系統自動產生的唯一識別符，用於區分不同的個人資料記錄。

## 使用者情境

### US-1 新增個人資料
身為**系統使用者**，我想要**提交我的基本資訊來建立一個新帳號或資料紀錄**，以便**後續能使用該身分進行操作**。

### US-2 查詢個人資料
身為**系統使用者**，我想要**透過 ID 查詢特定的個人資料**，以便**確認資料內容或驗證資料是否存在**。

### US-3 修改個人資料
身為**系統使用者**，我想要**更新我現有的個人資料（如更改姓名）**，以便**保持資訊的最新狀態**。

### US-4 刪除個人資料
身為**系統管理者**或**擁有權限的使用者**，我想要**永久移除某筆個人資料**，以便**清理無效資料或響應用戶的刪除請求**。

## 驗收條件

```gherkin
功能: 個人資料 CRUD 管理
    作為一名使用者，我需要能夠對個人資料執行增刪改查操作，以確保數據的正確性與完整性。

    場景大纲: 成功新增個人資料
        當我發送 POST 請求至 "/profiles"，內容包含:
            """
            { "name": "<姓名>", "email": "<電子郵件>" }
            """
        那麼回應的狀態碼應為 <狀態碼>
        並且回應標頭 "Location" 應存在且指向新建立的資源

        範例:
            | 姓名     | 電子郵件             | 狀態碼 |
            |----------|----------------------|--------|
            | 王小明   | wang@example.com     | 201    |
            | 李阿美   | li.mei@test.org      | 201    |

    場景: 新增重複電子郵件時失敗
        假設已存在一筆電子郵件為 "duplicate@test.com" 的個人資料
        當我發送 POST 請求至 "/profiles"，內容包含:
            """
            { "name": "新人", "email": "duplicate@test.com" }
            """
        那麼回應的狀態碼應為 409
        並且錯誤訊息應指出電子郵件已存在

    場景: 新增資料格式不合法
        當我發送 POST 請求至 "/profiles"，內容包含:
            """
            { "name": "", "email": "invalid-email" }
            """
        那麼回應的狀態碼應為 400
        並且錯誤訊息應指出欄位驗證失敗

    場景: 成功查詢存在的個人資料
        假設系統中已存在 ID 為 <id> 的個人資料
        當我發送 GET 請求至 "/profiles/<id>"
        那麼回應的狀態碼應為 200
        並且回應主體中的姓名應為 "<姓名>"
        並且回應主體中的電子郵件應為 "<電子郵件>"

        範例:
            | id   | 姓名     | 電子郵件             |
            |------|----------|----------------------|
            | 1    | 王小明   | wang@example.com     |

    場景: 查詢不存在的個人資料
        當我發送 GET 請求至 "/profiles/99999"（假設該 ID 不存在）
        那麼回應的狀態碼應為 404
        並且錯誤訊息應指出找不到該資料

    場景: 成功修改個人資料
        假設系統中存在 ID 為 <id>、姓名為 "<舊姓名>" 的個人資料
        當我發送 PUT 請求至 "/profiles/<id>"，內容包含:
            """
            { "name": "<新姓名>", "email": "<電子郵件>" }
            """
        那麼回應的狀態碼應為 200
        並且再次查詢該 ID 時，姓名應變更為 "<新姓名>"

    場景: 修改不存在的個人資料
        當我發送 PUT 請求至 "/profiles/88888"，內容包含:
            ```json
            { "name": "無名氏", "email": "noone@test.com" }
            ```
        那麼回應的狀態碼應為 404

    場景: 成功刪除個人資料
        假設系統中已存在 ID 為 <id> 的個人資料
        當我發送 DELETE 請求至 "/profiles/<id>"
        那麼回應的狀態碼應為 204
        並且隨後嘗試 GET 查詢該 ID 時應返回 404

    場景: 刪除不存在的資料
        當我發送 DELETE 請求至 "/profiles/77777"（假設該 ID 不存在）
        那麼回應的狀態碼應為 404
```

## API 概要

| HTTP 方法 | 路徑              | 描述             | 成功狀態碼 | 失敗狀態碼       |
|-----------|-------------------|------------------|------------|------------------|
| POST      | /profiles         | 新增個人資料     | 201 Created| 400 Bad Request, 409 Conflict |
| GET       | /profiles/{id}    | 查詢單一資料     | 200 OK     | 404 Not Found    |
| PUT       | /profiles/{id}    | 全量更新資料     | 200 OK     | 400 Bad Request, 404 Not Found |
| DELETE    | /profiles/{id}    | 刪除資料         | 204 No Content | 404 Not Found   |

## 範圍外
- 密碼管理與認證機制 (Authentication & Authorization)。
- 檔案上傳或頭像處理。
- 複雜的搜尋條件（如模糊搜尋、分頁），僅支援依 ID 精確查詢。
- 軟刪除邏輯，本需求採用硬刪除。
